# Stop Scan and subsequent manual wavelength control

## Observed behavior

The user reported that Stop Scan left Target Wavelength and Tracking disabled.
Authenticated Host/Worker metadata showed a completed stop_scan operation with
no pending work, but later controller motion readback remained tracking-on and
operation_complete=false. The UI therefore retained its motion lock. The old
driver sent scan STOP and returned panel control to LOC without stopping motor
tracking. An ACK did not establish motor completion.

## Change

The reusable native driver sends scan STOP, then tracking-off, then returns
panel control after successful acknowledgments. A failed or uncertain exchange
is not replayed. Stop does not command RESET, a return wavelength or emission
off. The Worker's target-following preference is preserved for the next manual
target; fresh completed motion readback releases the existing UI lock and uses
the actual stopped wavelength. The emitted light is not disabled by Stop.

Native regression covers stopping while OPC is busy, obtaining a new completed
readback, and then setting a new wavelength with following enabled. The browser
regression covers unlock after fresh stopped readback, target digit edits,
following toggles, scan shortcuts and narrow layouts using a finite intent
sink. It does not connect to hardware.

## Single-pass diagnostic preparation

Forward/Backward production capability remains false. A development-only
Code/Debugs CLI previews each stage by default. It uses the reusable driver,
exact controller/head identity, existing ownership guards and operating limits.
Enumeration, read-only connection and bounded motion each require independent
stage confirmation. No diagnostic has been executed against hardware.

An approved probe is limited to 0.10–0.25 nm at requested 0.05 or 0.10 nm/s.
Unknown RESET rate must fit the existing operator ceiling and head maximum.
Verified START and fresh origin cannot expand the approved span. Endpoint
arrival needs wavelength evidence as well as OPC. Hold needs multiple readbacks
conservatively spanning a full second, even with slow getters. A timeout sends
one disclosed STOP; it cannot imply arrival or enable a production capability.
Cleanup and controller readback are recorded separately from physical evidence.

## Normal switch after operator exit

authenticated snapshot showed DISCONNECTED, null connection ID, no resource
responsibility, zero pending work and a completed preserving-close receipt
bound to the current context (epoch 15). The helper's guarded
--stop-if-disarmed path then requested normal Host shutdown and confirmed
resource release and Worker exit. No process was forcibly terminated.

The qualified candidate App was launched visibly (PID 74564). New Host PID

confirmed activation, with no startup error. The saved laser remained
DISCONNECTED with null connection ID, no responsibility and no pending work.
Connections and outputs were not automatically restored. This establishes
the software switch and Host startup, not physical Stop behavior.
